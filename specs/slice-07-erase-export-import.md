# Slice 7 — Erase, JSON export, re-import

Corresponds to `sudoku-design.md` §6 step 7. Completes the admin surface slice 6
started, and closes the one gap that makes editing `001_schema.sql` a safe
operation rather than a destructive one.

**Estimated cost:** Medium (20–60k). Three features, but they share one page,
one transaction discipline, and one round-trip test.

**Blocked on:** slice 6.

**Needs, but is not blocked by, `D1`** — the same placeholder-names position as
slice 6. Erase is what finally clears the placeholder rows.

---

## 1. Why the three are one slice

`CLAUDE.md` binds them: erase is the schema-change path, the JSON export is the
precondition for erase rather than a nice-to-have, and re-import must exist
alongside export and be wired into the erase confirmation itself. Ship erase
without export and the first schema change costs the win history; ship export
without import and the file is a souvenir.

Slice 6 §1 already drew the cut in front of all three and said why the cut is
affordable there and nowhere later: until this slice lands, a schema change is a
file edit plus an unused family code. That escape hatch expires when slice 8
writes the first result, which is why this slice sits between them.

## 2. The schema this slice does not change, and the window it still has

`001_schema.sql` is unchanged by this slice. Slice 6 already declared `results`
with `game_id` as its primary key (§6 there) precisely so the round trip below
has a key that means the same thing in two databases — export carries it, import
dedupes on it, and there is no surrogate id to strip on the way out and reassign
on the way in.

What this slice still has is the *window*: no `results` row exists yet and
`players` is regenerated by **Run seed**, so if the round trip turns up something
the schema gets wrong, editing `001_schema.sql` here costs nothing. Slice 8
writes the first row anyone would miss, and from there the same edit costs an
export and an import (slice 8 §3).

Use the window if the tests below demand it. Do not go looking for schema work
to do in it — a column added on speculation is a column the import rule (§5) has
to carry forever.

## 3. Files

```
src/worker/
  admin.js         gains the export, import, and erase routes and their pages
src/db/
  export.js        pure: TABLES, canonical serialization, validateExport
  erase.js         pure: the drop-order loop, given list/drop functions
test/
  export.test.js
  import.test.js
  erase.test.js
```

The split is slice 6 §3's rule applied again: anything with logic in it takes
plain values as arguments and lives in a module `node --test` can import.
`erase.js` never touches `ctx.storage` — it is handed a `listTables()` and a
`dropTable(name)` and returns what happened, which is the only way this loop is
testable without a DO.

## 4. Export

### Route

`GET /r/<code>/admin/export`, an `<a>` on the admin page. Responds with the JSON
body, `Content-Type: application/json`, and
`Content-Disposition: attachment; filename="social-sudoko-<code>-<YYYY-MM-DD>.json"`.

A link rather than a form, and no client JavaScript: slice 6 §9's rule holds for
every page in this slice. The browser's own download is the whole mechanism.

### Format

```json
{
  "format": "social-sudoko-export",
  "version": 1,
  "room": "kitchen-table",
  "exportedAt": 1756800000000,
  "schema": [{ "name": "001_schema.sql", "checksum": "9f2c…" }],
  "tables": {
    "players": [{ "name": "…", "created_at": 1756000000000 }],
    "results": [{ "game_id": "…", "player": "…", "mode": "solo", "…": "…" }]
  }
}
```

- **`tables` is keyed by table name and ordered by `TABLES`**, a list in
  dependency order (`players`, then `results`) exported from `export.js`. Import
  reads the same list in the same direction, so a foreign key never arrives
  before its referent.
- **Columns come from `PRAGMA table_info(<table>)` on the live database**, not
  from a list in JavaScript. The point of the round trip is to survive an edit
  to `001_schema.sql`; a hardcoded column list would have to be edited in step
  with it, and the one time someone forgot would be the export taken before an
  erase.
- **`schema` records the ledger** — names and checksums — for diagnosis only.
  Import does **not** gate on it. §5's column rule says why gating there would
  refuse in exactly the case this slice exists to enable.

### Canonical serialization

The bytes must be a function of the data alone, because §6 fingerprints them.

- Top-level keys in the order shown; `tables` in `TABLES` order; row objects
  with columns in `table_info` order.
- Rows sorted by the table's primary key — `players` by `name`, `results` by
  `game_id` — with `Array.prototype.sort` given an explicit comparator. SQLite's
  row order is not a promise.
- `JSON.stringify` with two-space indentation. The file gets read by a human
  when something has gone wrong; a single line is not readable and the size
  difference is irrelevant at this scale.

**Scale.** A family playing daily for five years is under 10k rows and well
under a megabyte, so the whole export is built as one string in memory. This is
the assumption to revisit if it is ever false; nothing else in the slice depends
on it.

## 5. Import

### Route

`POST /r/<code>/admin/import`, from a `<form method="post"
enctype="multipart/form-data">` with a file input and a submit button. Workers
parse multipart bodies through `request.formData()`, so this needs no parser and
no dependency.

### Validation, which is most of the correctness here

`validateExport(json, { tableColumns, knownPlayers })` is pure and returns
either `{ ok: true, plan }` or `{ ok: false, errors }` — a list, not a first
error, because someone hand-editing an export wants all of them at once.

Refused outright:

- `format` not `social-sudoko-export`, or `version` not `1`.
- A key in `tables` that is not in `TABLES`.
- A row that is not an object, or a column value whose type contradicts the
  column's declared affinity — `INTEGER` wants `Number.isInteger`, `TEXT` wants
  a string. `NULL` is allowed only where the column is nullable.
- A `results` row whose `player` is neither in the file's `players` nor already
  in the database. The foreign key would catch this, but as a SQL error mid
  transaction rather than as a line saying which row and which name.
- A missing primary key value, or two rows in one table sharing one.

Not refused:

- **A table absent from `tables`.** A partial export is a valid file. Reported
  in the result, not treated as an error.
- **`room` differing from the room being imported into.** Moving a household to
  a new family code is a legitimate reason to hold a file, and refusing it would
  make the code a password, which §7.1 says it is not. The confirmation page
  says loudly which room the file came from and which room it is going into.

### The column rule

This is the rule that makes editing `001_schema.sql` survivable once data
exists, so it is stated as a rule rather than left to the code.

Let `E` be the columns present in the file's rows for a table and `S` the
columns the live schema declares.

- **`S \ E`** — a column the schema has and the file lacks. Filled by its
  declared default. If the column is `NOT NULL` with no default, refuse: there
  is nothing to put there, and inventing a value is worse than stopping.
- **`E \ S`** — a column the file has and the schema no longer does. **Refuse**,
  naming the columns, unless the operator ticks *discard columns not in the
  schema*. Dropping data silently during the operation that exists to prevent
  data loss is the single worst thing this slice could do.

`INSERT` names its columns explicitly and never relies on positional order.

**Why import does not check the schema checksums.** The intended sequence is
export → erase → *edit `001_schema.sql`* → apply → seed → import. After an edit
the checksums differ by design, so an import that demanded a match would refuse
in exactly the case it was built for. Column presence is the property that
actually matters, it is read from the live database, and it degrades gracefully
in both directions. The checksums are shown on the page so a surprising result
has an explanation to hand.

### Applying

- Refuse if any migration is **pending** or **drifted** (slice 6 §9's plan). The
  tables would be missing or the wrong shape, and a half-shaped import is worse
  than a refusal with a one-line fix.
- One `ctx.storage.transactionSync()` for the whole file, `TABLES` in order,
  every statement `INSERT … ON CONFLICT DO NOTHING`. It lands whole or not at
  all.
- Report per table: rows in the file, rows inserted, rows skipped as already
  present. "Skipped" is the number that tells you a re-import did nothing, which
  is what re-importing is supposed to do.

## 6. Erase

### The loop

`CLAUDE.md`: discover drop order by retrying until a pass drops nothing new; do
not hardcode it.

```js
eraseAll({ listTables, dropTable }) -> { dropped: string[], remaining: [{ name, error }] }
```

1. `listTables()` — `SELECT name FROM sqlite_master WHERE type='table'`, minus
   anything matching `sqlite_%` or `_cf_%`. Both prefixes are reserved by the
   runtime and neither is ours to drop; a loop that tries will report a failure
   that is not one.
2. Pass over the remaining names, `DROP TABLE` each, collecting the ones that
   throw.
3. If a pass dropped at least one table and any remain, run another pass.
4. If a pass drops nothing and tables remain, stop and return them with their
   errors. Do not loop forever, and do not claim success.

The whole loop runs inside one `transactionSync()`, so a stop at step 4 rolls
back to the database as it was. An erase that half-happened would be the one
state with no recovery path on this page.

`_migrations` is dropped like any other table — it was created by the file it
records (slice 6 §6), so dropping it makes every migration pending again, which
is what makes **Apply pending** rebuild from the files as they now read.

**Why not `ctx.storage.deleteAll()`.** It is one call, and it is the wrong
scope: it clears the DO's key-value side and any alarm along with the tables,
none of which this schema owns. The loop erases exactly what the migrations
created, and its failure mode is a list of table names on a page rather than a
DO in a state nobody planned.

### The confirmation, and what it actually guarantees

`GET /r/<code>/admin/erase` renders a page that:

- names the room in the heading, in the button text, and nowhere ambiguously —
  `CLAUDE.md` requires the page to say which room it is about to erase, and this
  is the press where that matters;
- shows the row count per table, so an accidental erase of the wrong room is
  visible as a count that does not match what you expected;
- offers **Download backup** — the §4 link, one click away, not a sentence
  telling you to go and take one;
- carries a hidden `fingerprint`: the SHA-256 of the canonical export bytes as
  of this page load;
- requires the room code typed into a text field before the button submits.

`POST /r/<code>/admin/erase` re-runs the export, recomputes the fingerprint, and
refuses on mismatch with "the data changed since this page loaded — reload and
re-export". It also refuses if the typed code is not this room's.

**What this does and does not prove.** It proves the confirmation is not stale:
you cannot erase against a backup offer that predates a write. It does not prove
anyone saved the file — a server cannot know that, and a spec that implied
otherwise would be lying about the guarantee. What is bought is that the export
is current, one click away, and that the erase you confirm is the erase you get.

### After

Redirect to the admin page, which renders its no-tables state (slice 6 §9) with
everything pending. The next two presses are **Apply pending** and **Run seed**.

## 7. The admin page grows

Slice 6 left it with two buttons and a status table. This slice adds, in this
order down the page: **Apply pending**, **Run seed**, **Download backup**,
**Restore from backup** (the file form), and last, visually separated, **Erase
everything** as a link to its confirmation page.

Erase is a link, not a form, because the destructive press must be the second
one and the first one must be the page that offers the backup. Slice 6 said the
button would not be rendered disabled in the meantime, and it was not.

## 8. Tests

Pure modules, `node --test`, no DO (slice 6 §10's position is unchanged).

1. **Canonical serialization.** The same rows in a different row order produce
   byte-identical output; a one-field change produces different output; column
   order follows `table_info` rather than object insertion order.
2. **Fingerprint.** Stable across two runs on equal data; differs after a single
   row changes; differs after a row is added.
3. **Validation, refusals.** One test per bullet in §5: bad `format`, bad
   `version`, unknown table, wrong-typed column, `NULL` in a `NOT NULL` column,
   a `results.player` in neither the file nor the database, a duplicate primary
   key, a missing primary key. Each error names the table and the row.
4. **Validation, acceptances.** A file missing a whole table; a file missing a
   column the schema has with a default; a file with an extra column *and* the
   discard flag set. And the negative of the last: extra column without the
   flag is refused.
5. **Round trip, pure.** Rows → export object → validate → insert plan → the
   same rows. Run over a fixture that includes every column type in the schema,
   a `NULL` in each nullable column, and a string containing a quote, a
   semicolon, and a newline — the three characters that break a serializer that
   was written by concatenation.
6. **Erase loop.** Against a fake `dropTable` driven by a dependency graph:
   drops everything droppable and returns them in the order it managed; two
   passes when the first is blocked; terminates and reports the remainder when a
   table can never be dropped; excludes `sqlite_%` and `_cf_%` names from the
   list it is given; a graph with no tables is a clean no-op.

Group 6 is the one that earns its keep. A retry loop with a wrong termination
condition either spins or reports success having dropped nothing, and there is
no DO in CI to catch either.

## 9. Acceptance criteria

The browser-marked ones need a deployment, like slice 6's. **Add them to
`questions.md` as a setup task when this slice starts**, as slices 1 and 6 did.

| # | Criterion | Closed by |
|---|---|---|
| 1 | `node --test` passes; the workflow is green. Test groups 1–6 exist. | CI |
| 2 | Export downloads a file whose name carries the room code and the date, and which opens as readable JSON. | **S-item** |
| 3 | Full round trip: seed, export, erase, apply, seed, import — the row counts match the export, and a second import inserts nothing. | **S-item** |
| 4 | The schema-change path: edit `001_schema.sql` to add a column, then export → erase → apply → seed → import. The new column holds its default, every old column survives. | **S-item** |
| 5 | Erase against a stale confirmation page (a write in between) is refused, and says why. | **S-item** |
| 6 | Erase with the wrong room code typed is refused. | **S-item** |
| 7 | Importing a file with a column the schema lacks is refused and names it; ticking discard lets it through. | **S-item** |
| 8 | Importing while a migration is pending is refused. | **S-item** |
| 9 | After erase, the admin page renders the fresh-database state with no error — the same page slice 6 criterion 2 covered, reached from the other direction. | **S-item** |
| 10 | The game at `/` is still unchanged and still does not know rooms exist. | local |

Criterion 4 is the whole slice in one check. If it passes, `CLAUDE.md`'s
clear/delete schema path works end to end and nobody ever has to write an
`ALTER` chain. If it fails, nothing else here matters.

Criterion 3 is worth doing on a room with the placeholder players *and* a couple
of hand-written `results` rows inserted through a temporary seed file, so the
round trip is exercised on the table that will actually hold irreplaceable data.
Delete the temporary seed file afterwards — §8's test group 5 is where that
coverage lives permanently.

## 10. Explicitly not in this slice

Timing, results, best times, the stats page, the client learning a family code
(all slice 8). WebSockets and hibernation (slice 9). Any authentication on the
admin page — §7.1 has not changed and the erase confirmation, not a password, is
what makes this survivable. Scheduled or automatic backups: there is no alarm in
this project yet, and an export nobody pressed is a feature with no failure
report.
